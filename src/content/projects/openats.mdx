# El problema

Mi tesis principal es que el proceso debería adaptarse al candidato, no el candidato a un proceso desconocido. Los candidatos no saben qué hay detrás del proceso. ¿Una máquina? ¿Una persona? Nadie lo sabe si no se lo dicen.

Algunos CV son más fáciles de leer que otros. Las plantillas suelen estar optimizadas para que las lea una persona más que una máquina, y por eso tantos "mentores de carrera" hacen vídeos diciendo que necesitas un CV optimizado.

# Cómo funciona

1. **Entrada**: el candidato sube un PDF, DOCX, PNG o JPG a través de un endpoint público.
2. **Conversión**: el DOCX pasa a HTML y luego a PDF, el PDF se renderiza a PNG y las imágenes se codifican en Base64.
3. **Parsing**: un modelo de visión y lenguaje lee el CV como imagen y devuelve JSON estructurado.
4. **Matching**: un LLM compara el perfil extraído con la oferta e indica qué requisitos aparecen de forma explícita, con evidencias.
5. **Scoring**: el backend, no el modelo, calcula una puntuación de 0 a 100. Las habilidades obligatorias pesan un 70 %, las deseables un 15 %, y la experiencia, la formación y los idiomas otro 15 %.

Esto tiene varias consecuencias:

- No hace falta OCR.
- Los candidatos no tienen que adaptar su CV para que se pueda leer.
- La puntuación se puede explicar: el mismo resultado de matching siempre da el mismo número, y se traduce en anotaciones positivas, negativas y neutras para el reclutador.

El parsing y la evaluación se ejecutan en workers de BullMQ, así que un modelo lento no bloquea la petición HTTP.

# Seguridad y fiabilidad

## Prompt injection

Lo probé con prompt injections. Como es un VLM que ve la página renderizada, no puede ver las inyecciones en texto blanco que sí recogería un OCR. También probé inyecciones visibles, sin éxito. Creo que puede deberse al propio proceso y a los prompts: el prompt de matching solo permite al modelo comprobar si los requisitos aparecen de forma explícita, no juzgar al candidato. Fueron pruebas manuales, así que no son una garantía.

## No determinismo

Como el pipeline se basa en IA, no es determinista: el parsing y el matching pueden variar con la misma entrada, así que recomiendo leer los CV para confirmar el resultado.

## Sesgos y datos personales

El perfil extraído no tiene ningún campo para la foto del candidato, así que el paso de matching nunca la recibe. El modelo de parsing sí ve la página entera. El nombre y otros datos relevantes sí se incluyen.

# Arquitectura

El backend sigue Domain-Driven Design con puertos y adaptadores, en torno a agregados como `JobPosting`, `Candidate` y `Candidacy`. Una candidatura es una máquina de estados: avanza por el pipeline hasta que el candidato es contratado, rechazado o se retira, y el agregado hace cumplir esas transiciones.

La autenticación usa tokens JWT de acceso y de refresco, con permisos por rol cacheados en Redis.

# Personalización

El backend está desacoplado del frontend, lo que permite crear distintos frontends para la vista del candidato. Los proveedores de IA también están detrás de un puerto, así que el proveedor y los modelos se eligen por configuración.
